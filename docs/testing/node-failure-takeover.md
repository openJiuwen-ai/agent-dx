# 节点失效与恢复对账契约

2026-09-16，用户明确：Master 根据既有心跳超时判定节点失效，该节点的旧实例执行随之失效。Node Manager 恢复连接或进程重启后，以 Master 权威目录对账并清理失效执行。阶段4已实现心跳超时失效、原节点恢复对账清理与旧结果拒收；共享checkpoint的新代次分配、恢复调用、路由切换与重复请求处理已接通，Lima双独立网络/后端的真实FC跨节点验收已通过；目标Node Manager执行中重启与未提交执行清理也已通过；独立主机/K8s门禁另行验收。

## Master 的职责

1. 心跳超时后关闭该节点的调度资格，持久化节点会话及旧执行的失效状态，撤销旧路由。仅设置节点 unavailable 不足以完成此流程。
2. 失效后的旧会话、旧归属代次及旧执行不能通过迟到心跳、结果提交或 SQLite 补写重新变为有效。
3. 需要恢复的 Instance 使用新的执行代次重新调度，保持 Instance ID；恢复所需 checkpoint 必须已登记、未过期、可跨节点读取且兼容目标后端。
4. checkpoint 缺失或 local-only 时明确恢复失败，不从原始镜像重新创建。节点不可调度期间不把它的容量重新投入分配。
5. Master 重启后，已有节点先关闭路由和准入，并从恢复完成时开始等待一个心跳超时周期。期限内重新报到可正常对账；期限届满仍未报到则失效旧执行。迟到注册和结果提交同样先检查这段期限，不能绕过定时器。

## 超时前的正常进程重启

同一节点在心跳期限内重启 Node Manager 时，Master 通过 mTLS 调用原注册地址的 `NodeService.GetSession`，核对节点身份与新进程会话；原地址/代理地址必须保持一致。复核时不持有调度锁，提交注册时重新检查前任会话和期限。新会话先关闭准入并完成权威对账，保留仍有效的 backend，之后再恢复路由。旧会话的心跳和提交被拒绝。

如果原地址仍由旧会话服务、地址发生变化或不能复核，不能提前接续；若心跳已经超时，则先持久化旧执行失效，即使新的进程已启动也只能对账清理。`GetSession` 只验证服务会话，不改变实例状态，也不替代对账。

## Node Manager 的职责

1. 恢复连接时，旧进程会话被判失效也必须触发完整对账，不仅进程重启才对账。
2. 对账完成前关闭生命周期入口与新准入；获取 Master 完整目录后，将实际 backend 执行与 Instance ID、归属节点及执行代次逐一比较。
3. 已失效、已转移或代次落后的执行：退役本机绑定/会话，调用 RuntimeBackend 删除旧执行，清理本机占用。不能复用旧执行重新发布 Running，也不能把自动重启策略用于重新拉起它。
4. SQLite 日志不能覆盖 Master 的失效或转移决定；丢弃退役归属的补写记录。有效归属的日志继续遵守已有降级契约。
5. 清理失败时保持对账未完成和准入关闭，重试清理。受有效快照引用保护的制品不随旧执行无条件删除。

失效判定与物理清理是两个步骤：前者由 Master 在心跳超时后完成，后者由恢复后的 Node Manager 执行。跨节点恢复不以收到旧节点的停止确认作为前置条件；控制面不应将超时事件记录为已经观察到远端进程退出。

Master 暂时不可用时的 SQLite 降级行为，与 Master 已经作出的节点失效决定分别处理；一旦获取到权威失效记录，对账清理优先，不能以本地日志保留旧执行资格。

## TDD 验收顺序

- 节点超时：旧执行失效与路由撤销持久化；迟到心跳和提交不能复活旧执行。
- Node Manager 恢复连接/进程重启：发现原执行仍在，先清理再开放准入；清理失败保持关闭。
- 有效共享 checkpoint：新节点恢复同 Instance ID、新执行代次，发布新路由。
- 无 checkpoint、local-only、过期或不兼容 checkpoint：明确恢复失败。
- 恢复过程被 Master 重启或请求重试打断：不重复创建，不接受旧代结果；原节点之后恢复仍清理旧执行。

当前 `MasterRpc::expire_nodes` 调用 `Session::invalidate_node`，原子更新节点和旧执行结果，并保存 invalidated 标记；迟到注册/提交路径也会先检查超时。Node Manager 对账会废弃与权威终态冲突的已有控制器，SQLite 不补写到权威终态之上。`Session::reserve_recovery` 与 `MasterRpc::recover_instances` 已接通共享 checkpoint 的新代次分配/恢复；持久化计划、重复请求和源节点制品保护有组件测试。真实FC双节点六项及计划落盘后Master重启已通过，r5目标Node Manager执行中重启及未提交backend清理也已通过，见 [跨节点恢复](2026-09-16-cross-node-recovery.md)。
