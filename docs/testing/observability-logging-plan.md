## 阶段8A：实例数量与资源分配Metrics（优先）

首批已通过本地与Buildkite #17基础K8s验收，见[验收报告](2026-09-16-metrics-acceptance.md)；指标与配置见[实例资源Metrics](instance-resource-metrics.md)。实卡验证仍按阶段5待办推进。

| 范围 | 规划指标与口径 |
| --- | --- |
| 实例数量 | 按生命周期状态统计当前实例；排队请求单列；删除历史使用累计计数，不混入存活数量 |
| 资源容量 | CPU、内存、磁盘的可分配上限；GPU/NPU按类型和型号统计整卡数量 |
| 资源分配 | 同时覆盖待启动预留和运行实例占用，以资源账本为准；暂停是否释放资源按实际持有记录统计 |
| 可用资源 | 根据容量与账本计算，容量下降造成的超额占用单独可见；维护/失联节点标识不可调度，不视为空闲容量 |
| 状态可信度 | 节点可达性、资源采集年龄、数据是否过期；Master与节点对账差异可诊断 |

职责：Master提供集群/Domain调度目录及资源分配视图；Node Manager提供本机账本、准入状态和实际使用量。两个视图分开命名，聚合时避免重复累加。资源“分配量”与CPU/内存“实际用量”明确区分。

默认聚合标签控制在节点、域、状态、资源类型及设备型号；实例级明细单独配置，避免给每项聚合指标附加Instance ID。指标名称、单位和标签在实现前形成版本化清单；对照原实现逐项核对业务口径，不要求沿用旧命名。

验收：先用状态转换及账本测试验证创建、排队、预留、暂停、恢复、删除、重启与失联不重复计数；再在真实部署中采集指标，与API/资源账本核对。GPU/NPU计数规则可先做组件验证，实际卡分配仍需带卡环境。

## 阶段8B：日志采集与Trace

- 统一组件日志结构：时间、级别、组件/节点、操作及错误码；按需带Instance ID、请求ID、Trace ID与Span ID。
- 明确组件运行日志与实例stdout/stderr的来源、路径及归属；复用sandboxd/RRT既有实例日志通道，不假定Supervisor掌握guest内部日志文件。
- 提供进程部署及Pod部署的采集配置与示例。部署环境负责采集和存储，产品提供标准输出/文件、指标端点及Trace导出能力；外部采集后端选型另行确定。
- Trace覆盖创建调度、节点执行、状态提交及数据面请求；补齐HTTP/gRPC上下文透传、关键阶段埋点、可配置采样和导出。后台恢复等异步操作保留关联。
- 日志与Trace不写API Key等凭证或默认采集用户代码、文件正文；导出队列有界，采集端失联不阻塞实例生命周期，并暴露导出失败/丢弃计数。

验收：真实创建→执行→删除可关联日志与Trace，包含失败路径；验证采样配置、字段脱敏、采集端断连与恢复。新增能力先完成本地验收，再加入适用的基础K8s独立验收步骤。

## 阶段9：日志滚动与压缩

- 配置项：启用开关、大小阈值、时间周期、压缩开关、保留数量、保留时长及总容量上限；CLI统一校验并下发。
- 首批覆盖Supervisor管理的组件文件日志。实例日志通过其实际写入方接入；容器stdout由容器运行时管理滚动，避免同一日志由两方同时滚动。
- 滚动必须与实际写入方协调。当前子进程持有文件描述符，仅rename后新建文件不能切换写入目标；实现时需明确选用Supervisor接管输出或组件主动重开机制，并验证在途写入。
- 压缩只处理已关闭的历史文件；异步压缩限制资源消耗，成功后原子发布压缩文件。保留清理保护当前写入文件和处理中制品。
- 明确重启后的历史文件识别、未完成压缩处理、磁盘满和压缩失败行为；故障可诊断，不静默删除唯一副本。

验收：持续写入跨越多次大小/时间滚动，解压后核对正常路径日志顺序、完整性与不重复；覆盖重启、保留策略、压缩失败及磁盘容量受限。异常场景明确可保证的边界，不把进程强杀前未刷盘的输出视作已持久化。
